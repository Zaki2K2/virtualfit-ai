# First real Colab experiment — execution and acceptance

Status: prepared locally; no real GPU run or validated trained checkpoint exists yet.

## Execute in order
1. Locally run `python slm-engine/tools/package_training.py`. Open `slm-engine/notebooks/01_fashion_lora_colab.ipynb` in Google Colab, select a T4 GPU runtime, then connect. No access to your session is assumed.
2. Run GPU diagnostics, upload `slm-engine/runs/virtualfit-slm-training.zip` when prompted, and install dependencies. The ZIP includes package source, pinned config, all 72/11/17 training splits and the separate API evaluation corpus. Keep Colab's CUDA PyTorch. If `pip check` reports an unrelated preinstalled package conflict, resolve it in a fresh runtime before proceeding; do not ignore errors. Model work uses fresh subprocesses after installation.
3. Run tokenizer preflight. It downloads the pinned Qwen2.5-0.5B-Instruct tokenizer/config, verifies Qwen2 architecture and chat-template alignment, and checks all 100 examples against the 1024-token limit without truncation. No model weights are allocated before this passes.
4. Mount your Google Drive. Choose a new, empty `RUN` directory for this experiment (default `MyDrive/virtualfit-slm/experiment-v2`). Run the two-step smoke cell and reload/comparison cell. Require finite loss, changed LoRA parameters, nonempty adapter weights, a complete optimizer checkpoint and successful fresh model/adapter loading. The comparison records raw base/adapter responses; it is not a quality pass.
5. Run the 64-step training cell, which continues the smoke checkpoint. Plain fp16 LoRA, microbatch 1, accumulation 8, rank 8, length 1024, gradient checkpointing, learning rate 2e-4, seed 42; checkpoint every four steps. This is 512 example presentations, roughly seven passes over a tiny synthetic training set, so overfitting is likely. Do not increase steps automatically. Peak CUDA allocation is recorded. On OOM, restart the runtime to release memory and use a new run/config with reduced sequence length only if preflight still passes; optional QLoRA needs separately tested bitsandbytes. Never change optimization settings when resuming an existing run.
6. If disconnected, reconnect a GPU, rerun diagnostics/upload/install/preflight and mount the same Drive directory. Smoke and main cells select the latest completed `checkpoint-*`; hidden temporary checkpoint directories are ignored. Optimizer, scaler, RNG, ordering and step restore, and identity mismatches fail. A checkpoint at the target step can finalize an interrupted manifest write. Drive is persistent but not a transactional filesystem: verify files after reconnect and keep an independent copy before deleting anything. Cross-GPU bitwise reproducibility is not promised.
7. Run the full held-out comparison before merge. Inspect `heldout-base-vs-lora.json`: same eight test prompts, deterministic generation settings, original base with adapter disabled versus freshly loaded trained adapter, raw text, JSON/grounding validity, exact IDs/categories, loss and latency. No deterministic API fallback masks failures. These eight synthetic examples do not establish general quality; do not tune on them. Review advice, exclusions, unavailable inventory and inappropriate fit claims manually.
8. Run merge, pinned llama.cpp b11643 conversion and Q4_K_M quantization cells. Both F16 and Q4 GGUF files persist on Drive. Merge stays on ephemeral Colab storage and can be recreated from the persistent adapter. Downloads include candidate GGUF and training manifest; also retain paired evaluation JSON and the complete adapter/checkpoint directory. Conversion alone does not prove that llama.cpp can load or generate correctly.
9. Keep original runtime on 8081. Start only the isolated candidate on 8082: `python slm-engine/tools/runtime.py serve --variant candidate --model-path C:/path/custom.gguf`. Install the package locally with `python -m pip install -e slm-engine` if needed. Start `npx tsx apps/api/scripts/styling-benchmark-server.ts`; run `python -m virtualfit_slm.evaluate_suite --model base --split heldout --output docs/first-cloud-heldout-base.json`. Restart the clean fixture harness, then run the same command with `--model custom --output docs/first-cloud-heldout-custom.json`. Compare raw acceptance, fallback rates, grounding, exclusion compliance, latency and all existing registration gates on the frozen 102-case suite; evaluate the actual quantized artifact, not just the merged model. Require human review and runtime recovery after a timeout.
10. Only after all gates and loading tests pass, use the existing `virtualfit_slm.register_custom` command with `--gguf`, `--manifest`, `--baseline` and `--candidate` pointing to these artifacts. Do not overwrite the original GGUF, change production environment variables or enable the custom selector beforehand. A saved checkpoint is training evidence, not proof of improvement.

## Two live inference timeouts
Evidence: `docs/slm-v2-original-eight.json`, test-000 = HTTP 504 after 60.310 s; test-003 = HTTP 504 after 60.092 s. Completed model answers took 20.926, 18.403 and 49.263 s; disclosed fallback took 59.244 s; two catalog-policy responses took 0.294 and 0.106 s. Six completions matched expected IDs; reliability was 6/8, not a pass. The archived report does not contain native prompt/decode timing, CPU utilization or queue timing, so no single root cause is proven.

Current runtime uses CPU-only Q4_K_M, four threads, context 2048, parallel 1, batch 128/microbatch 64. Provider sends a grounded schema and up to 260 generated tokens with a 60-second deadline. Cancellation reaches fetch; immediate cancellation of native compute is not established. The slot can remain occupied after a deadline.

Safe performance experiments, in priority order:
- Keep a persistent warmed runtime, wait for model readiness and issue a fixture warm-up before measuring. Run benchmarks without vision workloads/builds competing for CPU/RAM. Record cold and warm timings separately; warm-up must not hide user-facing cold-start failures.
- Capture llama.cpp prompt/decode token counts, per-stage timing, queue wait and memory/CPU pressure for the same fixed prompts. These are missing from the old report. Verify the next request succeeds after a deliberately timed-out request; avoid automatic retries that could duplicate native work.
- On an isolated candidate, benchmark thread counts against physical cores (for example 2 and 4), CPU batch settings and supported GPU offload of the same GGUF. Retain exact schema, candidate inventory and preference checks; rerun quality and latency gates. Hardware acceleration is the most direct path to lower latency without intentionally reducing model precision or answer budget.
- Test supported prompt-prefix caching with identical system prefixes and inventory-aware isolation; prove outputs and tenant boundaries remain valid. Keep concurrency at one until native cancellation/recovery is demonstrated. Multiple API processes currently need shared scheduling before serving concurrent traffic safely.
- Retain the 260-token budget, current quantization, complete candidate metadata, constraints and validation. Cutting tokens, dropping inventory or more aggressive quantization can change quality. Increasing the deadline merely waits longer; it is not a performance fix. Never label a timeout fallback as a successful model response.

No production inference tuning was applied without measurement. Recommendations are hypotheses to test against the frozen suite, not measured speedups.
